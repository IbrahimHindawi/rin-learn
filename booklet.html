Chapter 1

How To Read A Lesson

Each lesson is a complete program. Read it once without changing anything, then compile it. After that, make one small change and compile again.

The loop is deliberately plain:

read the I
compile the I
change one thing
compile again
keep the diff tiny

A small loop makes the compiler feel like a conversation. If the error message is surprising, the lesson just found the next thing to learn.

Read

Start with names, types, and blocks. Ask what storage exists and who owns it.

Change

Make one edit at a time: a type, a count, a field, a branch, or a generic argument.

Check

Compile the lesson and keep the generated output available for later inspection.

Chapter 5

The Check Ritual

Use the check script whenever you change a lesson:

powershell -ExecutionPolicy Bypass -File scripts/check_all.ps1

It finds rin.exe through RIN_HOME, then PATH, then the packaged compiler folder. It compiles every lesson into build/gen.

If all is well, it ends with:

ok 14 lessons
A learning repo should keep this ritual boring. The interesting part is the source, not the build ceremony.

Related notes: how to read, the shape of I, and reflection and metaprogramming.

Chapter 6

The C Connection

Only after the I shape is clear do we name the older neighbor. C is C because it exposes storage, addresses, contiguous arrays, structs as layout, enum states, callable symbols, headers, object files, and platform linkage.

I keeps that physical model visible while making declarations more regular and giving tools generated metadata to work with.

cinclude "stdio.h"
#define I_LEARN_BONUS 7

puts: proc(text: *const char)->i32 = { external; }

Lesson 06 shows the boundary: cinclude brings in a header, external declares a symbol owned elsewhere, and the generated C under build/gen shows the platform-facing result.

Start with I source. Inspect generated C after the shapes make sense.
